Le problème WFC

Wave Function Collapse : technique de génération procédurale qui synthétise une grille de sortie à partir d'un petit échantillon, en imposant que chaque sous-grille N×N de la sortie existe dans l'échantillon.

Algorithme — vue d'ensemble

Cinq étapes principales, répétées jusqu'à convergence ou échec :

#ÉtapeDescription
1ExtractionÉnumérer les sous-grilles N×N uniques avec leurs fréquences
2CompatibilitésPour chaque paire (t₁, t₂) et offset, vérifier la superposition
3EntropieNombre de tuiles encore possibles par cellule (heuristique MRV)
4CollapseCellule min-entropie → choix aléatoire pondéré par fréquence
5PropagationBFS de type AC-3 propage les contraintes aux voisins
Le cycle 3-4-5 se répète jusqu'à ce que toutes les cellules soient collapsées (succès) ou qu'une contradiction apparaisse (échec).

Étapes 1 et 2 — Tuiles et compatibilités

Extraction des tuiles

Pour chaque position (r, c) de l'échantillon, on extrait la sous-grille N×N et on incrémente sa fréquence.

for r in 0..H-N:
  for c in 0..W-N:
    t = extract(sample, r, c, N)
    tiles[t].freq += 1

Sur l'échantillon 5×5 avec N=2 : 8 tuiles uniques.

Table de compatibilité

Précomputation : pour chaque (t₁, t₂, offset), tester si t₁ et t₂ sont compatibles sur leur zone de chevauchement.

compatible[t1][oy+OFF][ox+OFF]
  = liste des t2 compatibles
    avec t1 à l'offset (ox, oy)

Lookup O(1) pendant la propagation.

Étapes 3 à 5 — Résolution

Entropie & Collapse

  • Entropie(c) = nombre de tuiles encore possibles
  • On choisit la cellule de plus faible entropie > 1
  • Tirage aléatoire pondéré par fréquence parmi les tuiles possibles
  • Si entropie = 0 : contradiction → échec

Propagation BFS

  • File FIFO initialisée avec la cellule collapsée
  • Pour chaque cellule défilée : examiner ses voisins dans (2N-1)²
  • Retirer du voisin toutes les tuiles non supportées par la source
  • Si le voisin change → remettre en file
Style AC-3 (Arc Consistency) : chaque modification déclenche une re-vérification des voisins concernés.

Implémentation série en C++17

Choix de design

  • Code templaté : WFC<N, T>
  • N : taille des tuiles (compile-time)
  • T : type des valeurs (binaire, multi-valeurs)
  • Headers séparés pour série / OMP

V1 — première tentative

Architecture

  • #pragma omp parallel créé à chaque étape BFS
  • Tâche par voisin
  • #pragma omp critical(wave_update) englobant toute la mise à jour
  • File BFS protégée par omp_lock_t

Problèmes constatés

  • Le critical sérialise toutes les tâches
  • Aucun parallélisme effectif
  • Overhead de création des régions à chaque étape BFS
  • T=32 → 500× plus lent que la série
9 / 17

Difficultés rencontrées

1. Critical section globale inutile

La preuve d'absence de race a demandé une analyse fine : pour un src fixé, les dst_j = src + (oy_j, ox_j) sont tous distincts car les offsets sont distincts → pas de verrou nécessaire.

2. BFS : visited vs in_queue

Premier fix : ajouter visited[] pour éviter les doublons → bug. Dans WFC une cellule peut nécessiter plusieurs passes si ses voisins changent. La bonne sémantique : in_queue réinitialisé au défilement.

3. Overhead de création des régions parallèles

Sur ARM, réveiller des threads dormants coûte ~0.1 à 1 ms par région. Avec des milliers d'étapes BFS, cet overhead seul dépasse plusieurs secondes — plus que le calcul utile.

V2 — architecture finale

Une seule région parallèle

#pragma omp parallel
{
  while (!done) {
    #pragma omp for nowait
    for (cell : ...) // entropie

    #pragma omp single
    {
      collapse(...);
      while (!bfs.empty()) {
        for (j : voisins)
          #pragma omp task
            { propage src→dst_j }
        #pragma omp taskwait
      }
    }
  }
}

Invariant de sûreté sans verrou

  • Pour un src fixé, les dst sont uniques
  • Les tâches écrivent dans des cellules disjointes
  • wave[src] est en lecture seule
  • Résultats dans result[j] (index unique)
Aucun verrou nécessaire sur wave. La file BFS est mise à jour après le taskwait.

Pourquoi l'anti-scalabilité ?

Quatre causes identifiées :

(a) Granularité trop fine

8 tâches par étape BFS, chacune ~64 comparaisons booléennes (quelques ns). Overhead OpenMP par tâche : ~µs. Ratio défavorable d'un facteur 1000×.

(b) Dépendance séquentielle

Chaque collapse dépend de l'onde résultant de tous les précédents — la boucle principale est intrinsèquement séquentielle. Seul l'intérieur d'une itération peut être parallélisé.

(c) Faux partage sur result[]

Le vector<int> contigu fait tenir 16 éléments par ligne de cache. 8 threads écrivant simultanément → rebond de ligne de cache, latence multipliée.

(d) Cohérence cache sur wave

Toutes les tâches lisent wave[src] simultanément. Sur ARM, la diffusion d'une ligne à plusieurs cœurs ajoute de la latence par rapport à un accès local.

Pistes pour réellement scaler

1. Bitsets SIMD

Remplacer vector<bool> par uint64_t (si K ≤ 64 tuiles) : entropie en 1 instruction popcount, AND/OR vectoriels.

Gain attendu : ×10 à ×100

2. Multiple restarts

Lancer T résolutions indépendantes avec graines différentes, garder la première qui converge.

Scalabilité parfaite mais hors cadre du sujet.

3. Coarsening

Regrouper plusieurs cellules sources dans une même tâche. Difficile car les sources du BFS peuvent partager des destinations.

4. GPU / Kokkos

Déplacer entropie et table de compatibilité sur GPU. Calcul d'entropie sur 65k cellules en quelques µs.

Conclusion

Ce qui a été livré

  • Implémentation WFC complète et correcte en C++17 templaté
  • Version série + version parallèle OpenMP utilisant l'API task explicite
  • Support multi-valeurs gratuit via la généricité
  • Benchmarks sur cluster HPC avec analyse rigoureuse

Résultat principal

Anti-scalabilité identifiée, mesurée et expliquée par quatre mécanismes distincts. WFC à granularité fine est intrinsèquement difficile à paralléliser par tâches.

Comprendre pourquoi un algorithme ne scale pas est un résultat académique aussi valable que le faire scaler — il oriente le choix du modèle d'exécution adapté.
